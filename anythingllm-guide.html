02. 核心架構基石：Workspace (工作區) 多租戶與向量隔離

許多初學者在使用 AnythingLLM 時，最常問的問題是：「為什麼我不能直接上傳檔案就開始聊天？為什麼一定要建立 Workspace？」

在 AnythingLLM 的哲學中，Workspace (工作區) 是最核心的安全與資料邊界。一個 Workspace 就是一個獨立的「數位大腦」或「業務虛擬顧問」，它具備以下四重嚴格隔離特性：

🎯 Workspace 的四大獨立隔離維度
  1. 向量空間隔離 (Vector Space Isolation)：上傳至 Workspace A 的文件，絕對不會被 Workspace B 的檢索檢索到。避免了財務部門財報與研發部門源代碼的交叉污染。
  2. 系統提示詞與人設隔離 (System Prompt & Persona)：Workspace A 可以被設定為「資深專利審查律師，僅輸出法條引用」；Workspace B 可以被設定為「TypeScript 架構專家，輸出 Clean Code 與單元測試」。
  3. 模型路由隔離 (LLM Provider Override)：針對高機密度的 HR 薪資工作區，可以指派本機 Ollama 離線模型；針對需要極高推論能力的演算法架構工作區，可以指派 Claude 3.7 Sonnet。
  4. 超參數獨立調校 (Hyperparameters Tuning)：可為不同工作區分別設定 `Temperature` (溫度 0.0 ~ 1.0)、`Context Window` (上下文長度) 以及 `Chat History Limit` (記憶對話輪數)。

03. 本地桌面端快速上手 (Windows / macOS / Linux)

如果你是個人開發者、研究員，或希望在自己的工作站（Laptop / Workstation）上快速體驗零外洩的私有知識庫，AnythingLLM Desktop 是最快上手的途徑。

1. 下載與安裝

  • Windows：前往官方 GitHub Releases 或官網下載 `.exe` 安裝檔。建議安裝在高速 NVMe SSD 目錄中。
  • macOS：支援 Apple Silicon (M1/M2/M3/M4) 原生架構與 Intel x86。下載 `.dmg` 拖曳至 Applications 即可。
  • Linux：提供 `.AppImage` 格式。賦予執行權限即可運行： 
    chmod +x AnythingLLM-Desktop.AppImage
./AnythingLLM-Desktop.AppImage

2. 初始設定精靈 (Onboarding Wizard) 避坑指引

啟動應用程式後，會看到初始配置精靈。這裡有三個核心決策點：

  1. 選擇 LLM Provider：
    • 方案 A（純本地離線首選）：選擇 Ollama。Base URL 預設填入 http://127.0.0.1:11434。AnythingLLM 會自動抓取你在終端機已下載的模型清單（如 llama3.3:8b、deepseek-r1:14b 等）。
    • 方案 B（LM Studio 對接）：選擇 LM Studio。預設 URL 為 http://localhost:1234/v1，確保 LM Studio 已開啟 Local Inference Server。
    • 方案 C（雲端 API）：選擇 OpenAI、Anthropic 或 DeepSeek，輸入你的 API Key 即可。
  2. 選擇 Embedding Provider (向量嵌入模型)：

    向量模型決定了「文字搜尋的語意理解精準度」。強烈建議：

    • 若使用 Ollama，請在終端機先執行 ollama pull nomic-embed-text 或 ollama pull bge-m3，並在此處選擇 Ollama 的相應模型。
    • 若不想安裝額外模型，可直接選擇 AnythingLLM Built-in Embedder，系統會自動使用內建的開源輕量級嵌入引擎。
  3. 選擇 Vector Database (向量資料庫)：

    直接保持預設的 LanceDB！LanceDB 是一個用 Rust 開發的無伺服器 (Serverless) 嵌入式向量資料庫，直接以二進位檔案形式儲存於本地磁碟，零記憶體常駐開銷、免配置連線帳密，百萬量級向量檢索延遲低於 10ms。

04. 企業級 Docker 與 Docker Compose 生產部署全攻略

對於企業團隊或 Homelab 伺服器，單機桌面版無法支援多同仁連線與權限管理。此時Docker 容器化部署是標準生產解法。

1. 單容器快速運行指令 (`docker run`)

# 建立具名卷以持久化所有儲存資料 (向量庫、SQLite、上傳檔案)
docker volume create anythingllm_storage

# 啟動 AnythingLLM 容器
docker run -d \
  --name anythingllm \
  -p 3001:3001 \
  -v anythingllm_storage:/app/server/storage \
  -v /var/run/docker.sock:/var/run/docker.sock \
  --restart unless-stopped \
  mintplexlabs/anythingllm:latest
⚠️ 重點避坑：宿主機目錄掛載權限問題

如果你不使用具名卷，而是使用本機目錄掛載（如 -v /opt/anythingllm/storage:/app/server/storage），在 Linux 系統上常會遇到 EACCES: permission denied 報錯。這是因為容器內部以非 root 用戶運行。請務必在宿主機賦予權限：

sudo mkdir -p /opt/anythingllm/storage
sudo chown -R 1000:1000 /opt/anythingllm/storage
sudo chmod -R 775 /opt/anythingllm/storage

2. 生產級 Docker Compose 完整架構 (AnythingLLM + Ollama + NVIDIA GPU 直通)

以下是一套標準的企業級私有化部署設定檔，將 AnythingLLM 與 Ollama 打包在同一個私有網路內，並啟用 GPU 硬體加速：

services:
  # ==========================================
  # 1. AnythingLLM 核心應用服務
  # ==========================================
  anythingllm:
    image: mintplexlabs/anythingllm:latest
    container_name: anythingllm-app
    restart: always
    ports:
      - "3001:3001"
    environment:
      - SERVER_PORT=3001
      - STORAGE_DIR=/app/server/storage
      - JWT_SECRET=super-secret-jwt-key-change-this-in-production
      - DISABLE_TELEMETRY=true
    volumes:
      - anythingllm_data:/app/server/storage
    depends_on:
      - ollama
    networks:
      - ai-network

  # ==========================================
  # 2. Ollama 本地大模型推論引擎 (含 NVIDIA GPU 直通)
  # ==========================================
  ollama:
    image: ollama/ollama:latest
    container_name: ollama-engine
    restart: always
    ports:
      - "11434:11434"
    volumes:
      - ollama_models:/root/.ollama
    networks:
      - ai-network
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: all
              capabilities: [gpu]

volumes:
  anythingllm_data:
    driver: local
  ollama_models:
    driver: local

networks:
  ai-network:
    driver: bridge
🔍 Docker 內部通訊重要認知：位址該填什麼？

在 Docker Compose 環境中，AnythingLLM 容器要連接 Ollama，LLM Base URL 必須填入 http://ollama:11434（使用 service 名稱），而不是 http://127.0.0.1:11434 或 localhost！因為容器各自有獨立的 Network Namespace。

如果是桌面版連外部 Docker，或 Docker 連本機跑的 Ollama，請使用 http://host.docker.internal:11434，並確保 Linux 宿主機在 Compose 中配置了 extra_hosts: ["host.docker.internal:host-gateway"]。

3. 企業級 Nginx 反向代理與 SSL 配置 (支援 SSE 串流打字機)

在大模型對話中，SSE (Server-Sent Events) 串流傳輸是實現流式打字機效果的關鍵。如果 Nginx 未關閉 Buffer，前端對話會卡住直到整個回答結束才一次性跳出。以下是標準 Nginx 設定：

server {
    listen 80;
    server_name ai.yourcompany.internal;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name ai.yourcompany.internal;

    ssl_certificate /etc/nginx/certs/fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;

    # 上傳大檔案限制 (如 100MB 企業技術手冊)
    client_max_body_size 128M;

    location / {
        proxy_pass http://127.0.0.1:3001;
        proxy_http_version 1.1;

        # WebSocket 支援
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";

        # 基礎 Header 轉發
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 重要：關閉代理緩衝以支援 SSE 串流逐字輸出！
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 600s;
        proxy_send_timeout 600s;
    }
}

05. 文件攝取與全能知識庫管線 (Document Ingestion & RAG)

AnythingLLM 最強悍的競爭力之一，在於其原生內建的多格式解析與深度爬蟲管線。在過去，工程師必須自己調試 PyPDF2、pdfplumber、BeautifulSoup、python-docx，而 AnythingLLM 直接把這些處理全自動化。

1. 支援的多元數據源與解析機制

  • 結構化與非結構化文件：`.pdf`、`.docx`、`.txt`、`.md`、`.csv`、`.xlsx`、`.json`、`.epub`。特別是在處理 PDF 時，內建 OCR 引擎可識別掃描件中的圖像文字。
  • 深層網站爬蟲 (Web Scraper & Deep Crawler)：在文件上傳區點擊網址圖示，輸入網址（例如公司 Confluence 或內部 Wiki）。支援設定「爬取深度 (Depth)」與「最大頁數 (Max Pages)」，自動解析 DOM 去除雜訊與導航欄，轉化為純淨 Markdown 存入向量庫。
  • GitHub 倉庫全量解析 (GitHub Repo Sync)：輸入 GitHub 公開或私有倉庫網址與 Access Token，AnythingLLM 會自動遞迴拉取所有代碼文件（.py、.js、.ts、.go 等），並建立代碼語義索引。
  • YouTube 影片與音訊 (YouTube & Whisper)：輸入 YouTube 連結，系統自動解析字幕或透過內建 Whisper 進行音訊轉文字，直接將數小時的演講轉化為可隨時檢索的知識庫。

2. 文本切塊 (Chunking) 的黃金參數法則

文件上傳後，系統會將長文切分成多個小型片段（Chunks）。切塊策略直接決定了檢索召回率與理解精準度：

原始長文件 (10,000 字) │ ├──► [ Chunk 1: 1000 Tokens ] ──────────┐ │ ▲ │ Overlap (重疊區 200 Tokens) ├──► └─────────► [ Chunk 2: 1000 Tokens ] ──────────┐ │ ▲ │ Overlap (200 Tokens) └──► └─────────► [ Chunk 3: 1000 Tokens ]
  • Chunk Size (切塊大小，建議 500 ~ 1000 Tokens)：
    • 太小 (< 200 Tokens)：上下文割裂，檢索出來的片段只是一兩句話，模型無法理解段落的真正含意。
    • 太大 (> 2000 Tokens)：語意過度發散，向量相似度被稀釋，且多個片段會迅速塞滿 LLM 的上下文視窗。
  • Chunk Overlap (重疊率，建議 10% ~ 20%，約 100 ~ 200 Tokens)：
    • 確保跨邊界的關鍵句（例如一句話剛好被切成兩半）不會遺失前後因果關係。

06. 對話雙模式 (Query vs Chat) 與向量檢索精準調校

AnythingLLM 與普通聊天軟體最大的分水嶺，就是其工作區內的兩種對話模式開關：

🚨 Query Mode (嚴格查證模式)：零幻覺的企業剛需

在 Query 模式 下，AnythingLLM 在組裝 System Prompt 時會向底層模型注入極度嚴格的約束：

"You are a helpful assistant. Only answer the user query based SOLELY on the provided context excerpts below. 
If the answer cannot be found directly in the text, you MUST explicitly respond with: 
'依據現有文件庫，無法找到相關資訊。' Do NOT use your own external knowledge or hallucinate."

適用場景：法規規章、藥物使用說明、公司報銷標準、金融審計。只要文件沒寫，AI 就絕對不胡說八道，徹底根除大模型胡言亂語的資安風險。

💬 Chat Mode (常規增強模式)：融合全球知識的創意顧問

在 Chat 模式 下，檢索出的文件片段僅作為「優先參考背景」。如果文件中沒有提及，模型會動用自身的通用訓練知識來補充回答，並嘗試發散推論。

適用場景：頭腦風暴、軟體架構重構構想、競品分析比較、文案潤飾。

向量檢索的核心調校參數 (Workspace Settings)

在 Workspace 的「Vector Database Settings」設定頁中，有兩組關鍵參數直接影響回答品質：

  1. Similarity Threshold (相似度門檻，建議 0.20 ~ 0.35)：
    • 這代表向量餘弦相似度 (Cosine Distance) 的截斷標準。
    • 調得太高 (如 > 0.6)：過度嚴格，稍微不同詞彙（如「報銷」與「費用核銷」）就無法召回片段，導致模型一直說找不到資訊。
    • 調得太低 (如 < 0.1)：不管問什麼都會拉出一堆不相關的廢話片段，浪費 Context Token 甚至干擾模型推理。
  2. Max Context / Top-K (最大片段召回數，建議 4 ~ 8 個片段)：
    • 代表每次查詢時，從向量庫挑選出最相關的幾段文字送給 LLM。
    • 若模型上下文較大（如 Claude 或 Qwen 32k/128k），可設為 6~10，提供更完整的背景事實。

08. 企業級多用戶 RBAC 權限體系與安全審計

在 Docker 生產環境中，開啟多用戶模式（Multi-User Mode）後，AnythingLLM 提供了三層嚴謹的角色型存取控制 (Role-Based Access Control, RBAC)：

角色 (Role) 系統全域設定 工作區管理 文件上傳與切塊 使用者與密碼管理 對話存取範圍
Admin (超級管理員) 完整權限 (LLM、向量庫、API Key) 新增 / 編輯 / 刪除任何工作區 完全控制 邀請 / 凍結 / 重設 全系統所有工作區
Manager (專案經理) 禁止 管理獲指派之工作區 可在獲授權工作區上傳/刪除文件 禁止 獲指派之特定工作區
Default User (一般成員) 禁止 禁止 (無法看到設定面板) 僅唯讀 (無法刪除或改動知識庫) 禁止 僅能在被分配的工作區內發起對話

工作區存取控制清單 (Workspace Access Control)

管理員可以在各個 Workspace 的「User Access」標籤中，針對特定用戶或群組開啟或關閉權限。未獲授權的用戶登入系統後，在側邊欄連該 Workspace 的名稱與存在都無法感知，徹底做到安全防護與資安合規。

09. 開發者 REST API 與 Web Widget 網站無縫嵌入

1. API 金鑰產生與鑑權

以 Admin 身分進入 Settings ➔ Tools ➔ Developer API，點擊 Generate New API Key。所有的 HTTP 請求均需附帶此 Token：

Authorization: Bearer YOUR_DEVELOPER_API_KEY

2. 常用 API 端點與 Python 呼叫實戰

以下是使用 Python 呼叫特定 Workspace 發送對話並獲取串流文字的範例代碼：

import requests
import json

BASE_URL = "http://localhost:3001/api/v1"
API_KEY = "YOUR_DEVELOPER_API_KEY"
WORKSPACE_SLUG = "financial-regulations"

headers = {
    "Authorization": f"Bearer {API_KEY}",
    "Content-Type": "application/json"
}

payload = {
    "message": "請列出 2026 年最新員工差旅報銷的機票補助上限與憑證要求？",
    "mode": "query"  # 可選 "query" (嚴格查證) 或 "chat" (一般對話)
}

response = requests.post(
    f"{BASE_URL}/workspace/{WORKSPACE_SLUG}/chat",
    headers=headers,
    json=payload,
    stream=True
)

print(f"[*] 連線狀態: {response.status_code}")
for line in response.iter_lines():
    if line:
        data = line.decode('utf-8')
        # 解析串流事件資料
        print(data)

11. 常見踩坑排查 (Troubleshooting) 與工程最佳實踐

在生產部署與實際運行 AnythingLLM 時，工程師經常會遇到幾類棘手的邊界問題。以下是經由實戰提煉的避坑清單：

常見故障排查 (Troubleshooting)

⚠️ 故障 1：Docker 內的 AnythingLLM 無法連線至宿主機 Ollama (報錯 Connection Refused: 11434)

根本原因：Ollama 預設只監聽 127.0.0.1:11434，不接受非本機 IP 請求；且容器內的 localhost 指向容器自己而非宿主機。

解決方案：

  1. 在宿主機修改 Ollama 環境變數，使其監聽全介面： 
    # Linux systemd (/etc/systemd/system/ollama.service)
Environment="OLLAMA_HOST=0.0.0.0:11434"

# 或 Windows / macOS 在環境變數中新增 OLLAMA_HOST=0.0.0.0:11434 並重啟 Ollama
  2. 在 AnythingLLM 的 Ollama Base URL 填入 http://host.docker.internal:11434（若兩者在同一個 Compose 網路則填 http://ollama:11434）。
⚠️ 故障 2：檔案已上傳且向量化成功，但 Query 模式永遠回答「找不到資訊」

根本原因：Workspace 內的 Similarity Threshold (相似度門檻) 設定過高，或者文字切片 (Chunk Size) 切分不合理。

解決方案：進入 Workspace 設定 ➔ Vector Database ➔ 將 Similarity Threshold 從原本的 0.7 降至 0.20 ~ 0.30。另外檢查上傳的 PDF 是否為純掃描圖片檔（若未啟用 OCR，萃取出來的純文字會是一片空白）。

⚠️ 故障 3：LanceDB 向量資料庫損毀或鎖定 (Lock file active)

根本原因：伺服器異常斷電或 Docker 容器被強行 kill -9 終止，導致 LanceDB 的 lock 文件未正常釋放。

解決方案：停止容器，進入儲存目錄下清理殘留 lock 檔案： 

docker stop anythingllm
cd /app/server/storage/vector-cache/lancedb  # 或具名卷目錄
find . -name "*.lock" -delete
docker start anythingllm

十條生產環境工程最佳實踐 (Best Practices)

  1. 定期備份 Storage 卷：AnythingLLM 的所有核心數據（SQLite 資料庫、工作區定義、LanceDB 向量資料）全都集中在 /app/server/storage 目錄下。只需對該目錄執行定時 tar.gz 備份，即可達成完整的災難復原。
  2. 嚴格控制 Context Window 上限：不要無腦把 Context 開到 128k。過大的 Context 會顯著拉長推論前綴處理 (Prefill Time) 延遲，導致首字反應時間 (TTFT) 飆升至 10 秒以上。建議設在 8k ~ 16k。
  3. 混合 Embedding 策略：中文內部文件優先使用 bge-m3；純英文或代碼庫優先使用 nomic-embed-text。
  4. PDF 上傳前進行預處理：對於包含大量複雜雙欄排版、跨頁長表格的技術手冊，先用外部工具（如 MinerU 或 Marker）轉化為結構清晰的 Markdown 再上傳，檢索召回率能提升 40% 以上。
  5. 分權管理與密碼安全：生產環境切勿使用預設密碼，並儘早透過環境變數配置強隨機 JWT_SECRET。
  6. 善用 Document Pinning (文件鎖定)：被 Pin 住的文件會強制將全文或重要段落保留在系統背景 Prompt 中，適用於公司簡介、統一術語表等每個對話都需要參照的通用規範。
  7. 關閉反向代理緩衝 (Proxy Buffering)：務必在 Nginx 中設定 proxy_buffering off;，否則對話無法實現流式打字機效果，用戶體驗極差。
  8. 為 Ollama 設定並發上限：多用戶同時提問時，Ollama 預設排隊可能超時。可透過 OLLAMA_NUM_PARALLEL=4 允許同時處理多個用戶請求（需預留足夠顯存）。
  9. 定期審計日誌：在 Admin 面板的 Logs 中檢視系統日誌，監控是否有惡意提示詞注入 (Prompt Injection) 或異常高頻率的 API 調用。
  10. 善用 Agent Slash Commands：在對話中教導同仁使用 /reset 清空上下文重啟思路，保持每輪業務諮詢的精確聚焦。
