GitHub Actions 完全攻略：原生 CI/CD 與自動化工作流指南

2026-10-06 · 15 分鐘閱讀
GitHub GitHub Actions CI/CD DevOps 教學
🎯 重點摘要：
  ① 什麼是 GitHub Actions：GitHub 內建的原生自動化與 CI/CD 平台，不需額外架設 Jenkins 等工具。
  ② 核心概念：由 Workflows (工作流)、Events (事件)、Jobs (工作)、Steps (步驟)、Actions (動作)、Runners (執行環境) 組成。
  ③ 優勢：無縫整合 GitHub、有龐大的社群開源 Actions 生態系、公開專案完全免費。
  ④ 實戰應用：自動化測試 (CI)、自動化部署 (CD)、自動標記 Issue、發布 Release 等。

為什麼需要 GitHub Actions？

在過去，如果你想要做持續整合與持續部署（CI/CD），通常需要自己架設 Jenkins 伺服器，或者註冊 CircleCI、Travis CI 等第三方服務，然後把 GitHub 上的程式碼與這些服務綁定。這不僅增加了維護成本，還容易遇到權限認證與網路同步的問題。

GitHub Actions 打破了這個局面。身為 GitHub 官方推出的原生功能，它允許你在 .github/workflows 目錄下直接撰寫 YAML 設定檔，只要有程式碼推入（Push）、開啟 Pull Request (PR)，或是定時觸發，GitHub 就會自動分配一台機器（Runner）幫你跑腳本。一站式的體驗讓它成為現代開發者的首選。

核心概念拆解

在開始寫 YAML 之前，我們必須先搞懂 GitHub Actions 的幾個核心名詞：

  • Workflow (工作流)： 一個完整的自動化流程。一個儲存庫可以有多個工作流（例如：一個用來測試、一個用來部署）。由 .github/workflows/ 底下的 YAML 檔案定義。
  • Event (事件)： 觸發 Workflow 執行的條件。例如：push、pull_request、schedule (定時) 或 workflow_dispatch (手動觸發)。
  • Job (工作)： 一個 Workflow 包含一個或多個 Job。預設情況下，多個 Job 會並行 (Parallel) 執行，但你可以設定它們的相依性（例如：Deploy Job 必須等 Test Job 成功才能執行）。
  • Step (步驟)： 每個 Job 裡面的具體步驟。可以是一條 Shell 指令（如 npm install），也可以是一個 Action。
  • Action (動作)： 已經寫好的可重複使用腳本。你可以用官方提供的 Actions，也可以用社群開源的 Actions（如：actions/checkout 用來拉取程式碼）。
  • Runner (執行環境)： 執行這些 Job 的伺服器。GitHub 提供免費的 Ubuntu、Windows、macOS 虛擬機，你也可以自建 Self-hosted Runner。

第一個 Workflow：自動化測試 (CI)

讓我們從一個最常見的情境開始：每當有人推程式碼到 main 分支時，自動執行 Node.js 的測試。

在專案根目錄下建立 .github/workflows/ci.yml：

name: Node.js CI

# 觸發條件 (Event)
on:
  push:
    branches: [ "main" ]
  pull_request:
    branches: [ "main" ]

jobs:
  build:
    # 執行環境 (Runner)
    runs-on: ubuntu-latest

    steps:
    # Step 1: 匯出程式碼
    - name: Checkout repository
      uses: actions/checkout@v4

    # Step 2: 設定 Node.js 環境
    - name: Use Node.js
      uses: actions/setup-node@v4
      with:
        node-version: '20.x'
        cache: 'npm' # 自動快取 npm dependencies 提升速度

    # Step 3: 安裝依賴
    - name: Install dependencies
      run: npm ci

    # Step 4: 執行測試
    - name: Run tests
      run: npm test

語法解析：

  • on: 定義了觸發條件，這裡是當 main 分支有 Push 或 PR 時觸發。
  • runs-on: ubuntu-latest 告訴 GitHub 給我一台最新的 Ubuntu 虛擬機。
  • uses: actions/checkout@v4 這是官方提供的 Action，幫你把程式碼拉到 Runner 裡面。幾乎每個 Workflow 都要用到它。
  • run: npm test 則是直接在 Runner 裡面執行的終端機指令。

常用觸發條件 (Events)

Event說明範例語法
push當有程式碼 Push 到特定分支時on: push
pull_request當 PR 被開啟、更新或同步時on: pull_request
scheduleCron 排程，定時自動執行on: schedule: - cron: '0 0 * * *' (每天半夜執行)
workflow_dispatch允許在 GitHub 網頁上按按鈕手動觸發on: workflow_dispatch:
release當發布了新的 GitHub Release 時on: release: types: [published]

環境變數與 Secrets 安全管理

在 CI/CD 過程中，我們經常需要用到 API Key、資料庫密碼或伺服器的 SSH Key。千萬不能把它們直接寫在 YAML 裡面！

GitHub 提供了 Secrets 功能。到專案的 Settings > Secrets and variables > Actions 新增你的機密資訊（例如 DOCKER_PASSWORD）。

在 YAML 中讀取 Secret：

steps:
  - name: Login to Docker Hub
    uses: docker/login-action@v3
    with:
      username: ${{ secrets.DOCKER_USERNAME }}
      password: ${{ secrets.DOCKER_PASSWORD }}

若是普通的環境變數（非機密），可以使用 env 關鍵字：

env:
  NODE_ENV: production
  API_URL: https://api.example.com

進階實戰：自動建置與部署 (CD) 到伺服器

現在我們要設計一個串聯的 Workflow：先跑測試（Test），測試成功後，再自動部署（Deploy）到遠端伺服器。

name: CI/CD Pipeline

on:
  push:
    branches: [ "main" ]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20' }
      - run: npm ci
      - run: npm test

  deploy:
    runs-on: ubuntu-latest
    # 關鍵：告訴 GitHub 這個 job 依賴 test job，test 成功才會跑 deploy
    needs: test 
    steps:
      - uses: actions/checkout@v4
      
      - name: Deploy to Server via SSH
        uses: appleboy/ssh-action@v1.0.3
        with:
          host: ${{ secrets.SERVER_HOST }}
          username: ${{ secrets.SERVER_USER }}
          key: ${{ secrets.SSH_PRIVATE_KEY }}
          script: |
            cd /var/www/my-app
            git pull origin main
            npm install
            pm2 restart my-app

這裡用到了 needs: test，確保如果測試失敗，就不會進行部署。同時使用了社群知名的 appleboy/ssh-action 來透過 SSH 登入遠端伺服器執行部署指令。

實用技巧與最佳實踐

  1. 善用 Actions Marketplace： 不要重新發明輪子。想做什麼（如部署到 AWS、發送 Slack 通知），先去 GitHub Marketplace 搜尋，通常都有現成的 Action 可以 uses。
  2. 鎖定 Action 的版本： 建議使用 @v4 這樣的大版本號，或者直接鎖定 Commit SHA，避免 Action 開發者引入 breaking changes 導致你的 Workflow 壞掉。
  3. 矩陣測試 (Matrix Strategy)： 如果你的套件需要支援多個 Node.js 版本，不需要寫多個 Job，使用 matrix： 
    strategy:
  matrix:
    node-version: [18.x, 20.x, 22.x]
steps:
  - uses: actions/setup-node@v4
    with:
      node-version: ${{ matrix.node-version }}
  4. 快取 (Caching)： 對於 node_modules 或 Docker layers，善用 cache 可以讓你的 CI 時間從幾分鐘縮短到幾十秒。官方的 actions/setup-* 通常都已經內建快取選項（如前面範例的 cache: 'npm'）。

總結

GitHub Actions 把自動化流程與程式碼放在一起管理（Configuration as Code），大幅降低了 DevOps 的門檻。從簡單的 Linter 檢查、單元測試，到複雜的跨平台編譯打包、Docker 映像推送與 Kubernetes 部署，都能夠輕鬆搞定。現在就打開你的 GitHub 專案，點擊上方的 "Actions" 標籤，挑選一個官方推薦的範本開始嘗試吧！
