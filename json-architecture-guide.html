💡 一、什麼是 JSON？誕生背景、RFC 8259 規範與核心優勢

JSON 全稱為 JavaScript Object Notation（JavaScript 物件標記法），最初由 Douglas Crockford 於 2000 年代初期推廣，並最終正式收錄於網際網路標準規範 RFC 8259 以及 ECMA-404。它是一種基於純文字的「輕量級資料交換格式（Lightweight Data-Interchange Format）」。

在 JSON 問世之前，網路世界的資料交換幾乎被 XML（eXtensible Markup Language） 與 SOAP 協定統治。然而，XML 充斥著冗長繁複的開閉標籤（如 <user><id>101</id><name>Alice</name></user>）、龐大的傳輸頻寬消耗，以及在瀏覽器端解析時繁重的 DOM 解析開銷。JSON 的出現直接顛覆了這一局面：它完美借鑒了 JavaScript 簡潔的物件字面量語法，既易於人類閱讀與編寫，又極易於機器解析與生成。

📐 二、JSON 底層架構與語法規範（Syntax & Data Types）

JSON 雖然源自 JavaScript，但它是一門完全獨立於語言的文字規範。根據 RFC 8259，一個合法的 JSON 文字必須由以下「兩種核心資料結構」與「六種原生基本型別」組合構建：

📦 1. 物件（Object）

由一對大括號 { } 包裹的無序「鍵/值對（Key/Value Pairs）」集合。每個鍵（Key）必須是嚴格雙引號包裹的字串，鍵與值之間以冒號 : 分隔，鍵值對之間以逗號 , 分隔。

📑 2. 陣列（Array）

由一對中括號 [ ] 包裹的有序「值清單（Ordered List of Values）」。陣列內的元素可以是任意合法的 JSON 資料型別，甚至容許混合不同型別，元素之間以逗號 , 分隔。

JSON 六大原生合法資料型別

請牢記：JSON 的世界只有以下 6 種合法型別，任何超出此範圍的值在原生 JSON 中皆屬於非法語法：

  • 字串（String）： 必須使用雙引號 " " 包裹。支援反斜線跳脫（如 \"、\\、\/、\n、\r、\t、\uXXXX Unicode 碼點）。單引號 ' ' 在 JSON 中是完全非法的語法錯誤！
  • 數值（Number）： 雙精度浮點格式。支援整數（如 42）、負數（如 -17）、小數（如 3.14159）以及科學記號（如 1.2e+5、-4.5e-3）。不支援八進位前綴（如 0777）、十六進位（0xFF）、NaN 或 Infinity。
  • 布林值（Boolean）： 僅有全小寫的 true 或 false。不允許縮寫、數字表示（1/0）或首字母大寫（如 Python 的 True/False）。
  • 空值（Null）： 僅有全小寫的 null，代表無值或空參考。
  • 物件（Object）： 巢狀結構 { "key": value }。
  • 陣列（Array）： 巢狀結構 [ value1, value2 ]。

⚠️ JSON 不支援的資料型別與失真陷阱

目標語言原生型別 原生 JSON 是否支援？ 預設序列化後的常見後果（以 JavaScript 為例） 工程防禦與標準實踐
undefined 不支援 在 Object 中該鍵值會直接被靜默丟棄；在 Array 中會被轉換為 null 明確賦值為 null，避免鍵值丟失導致前後端契約斷裂。
Date (日期時間) 不支援原生型別 自動調用 toISOString() 轉成純字串 "2026-10-16T08:00:00.000Z" 反序列化時它依然只是純字串，必須手動透過 Date 剖析器或 reviver 還原。
Function / 方法 嚴格禁止 直接被忽略丟棄，若在陣列中則變為 null JSON 是純資料表示層，不得傳輸可執行程式碼（避免遠端程式碼執行安全漏洞）。
RegExp (正規表示式) 不支援 被序列化為空物件 {} 應先轉換為 pattern 字串再行傳輸。
NaN / Infinity 非標準數值 被直接強制轉換為 null 除零錯誤或算術溢位後直接送出會污染資料庫，應在序列化前完成數學防禦。
BigInt (大整數) 不支援 TypeError: Do not know how to serialize a BigInt 直接崩潰 雪花演算法（Snowflake ID）等大於 53-bit 整數必須轉為純字串傳輸！

三大語法「天條」：絕不可觸碰的語法地雷

/* ❌ 錯誤示範：三個致命的 JSON 語法錯誤 */
{
  'name': 'Bob',              // 錯誤 1：鍵與字串值使用了單引號，必須使用雙引號 "name": "Bob"

{
  "name": "Bob",
  "age": 30,
  "isAdmin": false
}

🔄 三、JSON 操作核心概念：序列化（Serialization）與反序列化（Deserialization）

在所有程式語言中，我們與 JSON 打交道的核心就是兩個方向的型態轉化：

1
序列化（Serialization / Stringify / Marshalling / Encoding）

將執行時期記憶體中的複雜資料結構（如 JavaScript Object、Python Dict、Go Struct）轉換為跨平台、可儲存或網路傳輸的純文字字串（UTF-8 String）或位元組流（Byte Stream）。

2
反序列化（Deserialization / Parse / Unmarshalling / Decoding）

從網路封包或檔案磁碟中讀取未經加工的 JSON 字串，經過語法剖析器（Lexer & Parser）驗證文法後，重新構建回該語言的原生記憶體物件實體。

4.2 Python：內建 json 模組與百萬吞吐極致優化

Python 內建的 json 模組提供了四個關鍵方法：dumps / loads（記憶體字串操作）與 dump / load（檔案 Stream 讀寫）：

import json
from datetime import datetime, date
from uuid import UUID, uuid4
from decimal import Decimal

# 1. 處理自訂型別：繼承 JSONEncoder 解決 TypeError: Object of type Decimal is not JSON serializable
class HardcoreJSONEncoder(json.JSONEncoder):
    def default(self, obj):
        if isinstance(obj, (datetime, date)):
            return obj.isoformat()
        if isinstance(obj, UUID):
            return str(obj)
        if isinstance(obj, Decimal):
            return float(obj)
        return super().default(obj)

payload = {
    "transaction_id": uuid4(),
    "amount": Decimal("199.99"),
    "timestamp": datetime.now(),
    "is_settled": True
}

# 序列化：ensure_ascii=False 確保中文字元不被編碼為 \uXXXX
json_str = json.dumps(payload, cls=HardcoreJSONEncoder, ensure_ascii=False, indent=2)
print(json_str)

# 2. 高效能替代方案：面對高並發 Web 服務（FastAPI / microservices）
# Python 內建 json 為純 C 模組，但在處理大規模巨量 JSON 時已顯疲態：
# 🚀 推薦使用 orjson（Rust 編寫，效能高達內建 json 的 5~10 倍，原生支援 dataclass, datetime, numpy, UUID）
import orjson

fast_bytes = orjson.dumps(payload) # 直接產生 utf-8 bytes，零額外轉碼開銷
fast_dict = orjson.loads(fast_bytes)

4.3 Go 語言：靜態強型別、Struct Tags 與延遲解析

Go 語言透過 encoding/json 包與 反射（Reflection） 進行對映，是後端架構中處理 JSON 最嚴謹的範本：

package main

import (
	"encoding/json"
	"fmt"
	"time"
)

type UserProfile struct {
	ID        int64     `json:"id"`
	Username  string    `json:"username"`
	Email     string    `json:"email,omitempty"`    // 空值時在 JSON 中省略該 key
	SecretKey string    `json:"-"`                  // 完全隱藏，不參與序列化
	CreatedAt time.Time `json:"created_at"`
	Metadata  json.RawMessage `json:"metadata"`     // 🌟 延遲解析未知結構或動態 Payload
}

func main() {
	rawJSON := []byte(`{
		"id": 8802938491823,
		"username": "ironman",
		"created_at": "2026-10-16T08:00:00Z",
		"metadata": {"npu_tier": "extreme", "credits": 500}
	}`)

	var user UserProfile
	if err := json.Unmarshal(rawJSON, &user); err != nil {
		panic(err)
	}

	fmt.Printf("解析成功：用戶名 = %s, Metadata 未解構字串 = %s\n", user.Username, string(user.Metadata))
}

🛡️ 五、資料契約保證：JSON Schema 規範與 AI Agent Structured Outputs

JSON 本身是 無綱要的（Schema-less），這意味著客戶端可以送出任何型別的值而不受拘束。但在微服務架構與金融交易系統中，缺乏資料契約會造成災難。JSON Schema 應運而生，它是描述與驗證 JSON 資料結構的工業級 IETF 規範。

標準 JSON Schema 定義範例

{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "UserCreationContract",
  "type": "object",
  "properties": {
    "userId": {
      "type": "integer",
      "minimum": 1
    },
    "email": {
      "type": "string",
      "format": "email"
    },
    "tier": {
      "type": "string",
      "enum": ["free", "pro", "enterprise"]
    },
    "tags": {
      "type": "array",
      "items": { "type": "string" },
      "uniqueItems": true
    }
  },
  "required": ["userId", "email", "tier"],
  "additionalProperties": false
}

AI 時代的必修課：LLM Tool Use 與 Structured Outputs

在 2026 年，大語言模型（OpenAI GPT-4o / o1、Claude 3.5 Sonnet / Haiku、Google Gemini 2.0 Flash）已廣泛應用於自主 Agent 與工具呼叫（Function Calling）。AI 模型是如何確保輸出精確可執行的 JSON，而不是胡言亂語的？

背後的關鍵技術正是 JSON Schema 導引解碼（Constrained Decoding / Grammars）：在推理階段，推理引擎（如 vLLM、SGLang、Llama.cpp）會將開發者提供的 JSON Schema 轉換為 Context-Free Grammar (CFG) 或正則有限狀態自動機（FSM），在生成每一個 Token 的機率分佈（Logits）時，強制將違反 Schema 的 Token 機率遮罩為負無窮大（-inf），從而在數學理論層面上 100% 保證產生的 JSON 符合綱要規範！

🚀 六、進階衍生家族：JSON Lines (JSONL)、JSON5、JSON-LD 與 JSON Patch

隨著資料規模與應用情境的多樣化，標準 JSON 衍生出許多強大的特化家族：

📄 1. JSON Lines (.jsonl)

大數據與 AI 訓練之王。 每一行都是一個獨立、合法的標準 JSON 物件，中間以換行符 \n 分隔。最大優點是支援串流讀取（Streaming）與斷點續傳，處理數百 GB 的資料集無需一次性讀入記憶體。

⚙️ 2. JSON5

現代工程設定檔首選。 擴充了標準 JSON，允許單行與多行註解（//、/* */）、單引號包裹、允許結尾尾隨逗號（Trailing Comma）與十六進位數字，廣泛應用於 tsconfig.json 等工具鏈。

🌐 3. JSON-LD (Linked Data)

Web 3.0 與搜尋引擎 SEO 核心。 透過 @context 與 @type 賦予資料全局語意，Google 搜尋引擎正是透過網頁內的 JSON-LD 產生搜尋結果富文本摘要（Rich Snippets）。

🩹 4. JSON Patch (RFC 6902)

RESTful API PATCH 最佳實踐。 以微型指令陣列（如 add、remove、replace）精確描述 JSON 文件的局部增量修改，避免完整覆蓋傳輸帶來的高頻網路頻寬消耗。

⚠️ 七、生產環境五大高頻踩坑與除錯防禦實戰

坑 1：64-bit 大整數精度遺失（Snowflake ID 慘案）

在分散式系統中，資料庫常用的分散式主鍵（如 Twitter Snowflake ID、訂單編號）是 64 位元長整數（例如 1847192847192847193）。

在 JavaScript 中，數值採用 IEEE 754 雙精度浮點數儲存，其能精確表示的最大安全整數為 Number.MAX_SAFE_INTEGER（$2^{53} - 1$ = 9007199254740991，即 16 位數）。一旦超過此門檻，末幾位數值會自動被四捨五入歸零或錯位！

// 前端收到後端回傳的原始 JSON: {"orderId": 1847192847192847193}
const data = JSON.parse('{"orderId": 1847192847192847193}');
console.log(data.orderId); // 輸出 1847192847192847000 ── 精度丟失，訂單查詢直接 404！

// 💡 鐵則防禦：後端針對 64 位元整數（int64 / uint64）序列化時，必須強制轉換為「字串」傳遞！
// {"orderId": "1847192847192847193"}

坑 2：循環參照（Circular Reference）崩潰

const parent = { name: "Parent" };
const child = { name: "Child", parent: parent };
parent.child = child; // 形成物件雙向閉環循環引用

// 執行序列化直接丟出 Uncaught TypeError!
// TypeError: Converting circular structure to JSON
try {
  JSON.stringify(parent);
} catch (e) {
  console.error("循環引用爆炸：", e.message);
}

// 💡 防禦方案：使用 WeakSet 記錄已遍歷節點，或引入 flatted / cycle.js 套件解環

坑 3：原型鏈污染（Prototype Pollution）安全攻擊

在解析非信任來源的 JSON 並進行遞迴物件合併（Deep Merge）時，若惡意攻擊者傳入 "__proto__": { "isAdmin": true } 或 "constructor": { "prototype": { ... } }，可能竄改所有 Object 原型鏈的屬性，造成資安權限繞過或遠端程式碼注入！

防禦守則： 使用 Object.create(null) 建立無原型容器，或在合併邏輯中明確檢查並過濾 __proto__ 與 prototype 關鍵字。

坑 4：超大檔案記憶體暴增（OOM - Out of Memory）

當需要處理幾百 MB 甚至數 GB 的單一龐大 JSON 檔案時，切勿直接使用 JSON.parse(fs.readFileSync('huge.json')) 或 Python 的 json.load(f)，這會導致伺服器 V8 堆疊空間或 Python 行程瞬間 OOM 被作業系統強制中斷。

防禦守則： 採用基於事件推動的串流剖析器（Streaming Parser），例如 Node.js 的 stream-json、JSONStream，或 Python 的 ijson，以管線方式逐節點解析消費。

📋 八、總結與核心速查清單（Cheat Sheet）

  • 嚴格雙引號： 鍵名稱與字串值必須使用 " "，絕不可使用單引號。
  • 禁止尾逗號： 物件與陣列的最後一個元素後方絕對不能殘留逗號 ,。
  • 六大合法型別： String、Number、Boolean、Null、Object、Array。不支援 Date、undefined、Function、BigInt。
  • 雪花 ID 防禦： 任何 64-bit ID 或超過 15 位數的整數，一律以字串格式封裝傳遞。
  • 契約至上： 企業級 API 務必配套 JSON Schema，亦是現代 AI Agent Structured Outputs 穩定性的核心基石。
  • 效能極限： Python 面對海量資料使用 orjson，Go 善用 json.RawMessage 實施延遲反序列化。
