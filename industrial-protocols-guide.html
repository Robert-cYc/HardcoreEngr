工業通訊協定全解析：RS232/RS485, Modbus, DDE 到 OPC DA/UA

2026-10-03 · 15 分鐘閱讀

在工業自動化 (Industrial Automation)、智慧製造與工業物聯網 (IIoT) 的世界中，IT (資訊技術) 與 OT (營運技術) 的融合是必經之路。對於習慣了 HTTP/REST API、gRPC 與 WebSockets 的純軟體工程師來說，初次接觸工廠機台的通訊協定往往會感到一頭霧水。

機台為什麼沒有 IP 位址？什麼是鮑率 (Baud rate)？COM port 是什麼？為什麼讀取一個溫度值需要去了解暂存器 (Register)？本文將由淺入深，從最底層的物理硬體層，到網路資料鏈結層，最後再到軟體架構層，為您詳細拆解工業界最常見的通訊協定與介面：RS232、RS485、Modbus (RTU/TCP)、DDE 以及 OPC (DA/UA)。

第一層：物理介面層 (Physical Layer) 硬體接線

在工廠中，許多老舊機台或簡單的感測器 (如溫濕度計、流量計) 並不具備網路孔 (RJ45)，它們是透過序列通訊 (Serial Communication) 的方式進行資料傳輸。其中最主流的兩種實體介面就是 RS-232 與 RS-485。

1. RS-232：點對點的經典介面

RS-232 (Recommended Standard 232) 是非常古老的標準，早期的電腦主機板上常見的 9 針 (DB9) 介面就是它。

  • 通訊方式： 全雙工 (Full-Duplex)，可以同時收發資料。
  • 接線方式： 最基本需要三根線：Tx (傳送)、Rx (接收) 與 GND (接地)。
  • 連線拓樸： 點對點 (Point-to-Point)。一個 RS-232 接口只能連接一台設備。
  • 傳輸距離： 非常短，標準建議為 15 公尺以內，容易受到工廠電磁干擾 (EMI)。

2. RS-485：工業現場的抗干擾王者

為了解決 RS-232 距離短且只能一對一的問題，RS-485 誕生了。它是目前工廠底層感測器最廣泛使用的實體層標準。

  • 通訊方式： 半雙工 (Half-Duplex)，同一時間只能有一個設備發送，其他設備接收。
  • 訊號原理： 採用差分訊號 (Differential Signaling)，透過兩根線 D+ 與 D- 之間的電壓差來表示 0 或 1。這種設計極大增強了抗干擾能力。
  • 連線拓樸： 多點匯流排 (Multi-drop Bus)。一條線上通常可以串接 32 到 128 台設備（甚至更多）。也就是說，一台工業電腦可以透過一條線讀取幾十個感測器。
  • 傳輸距離： 可達 1200 公尺（在低鮑率下）。
💡 工程師白話文： RS232 就像是用兩根水管，一個專門送水一個專門排水，但管子很短只能接一家。RS485 像是一條長長的大水溝，沿途有幾十家工廠，但同一個時間只能有一家在講話，大家用大聲公廣播。

第二層：通訊協定層 (Protocol Layer) 資料格式

有了 RS-232 或 RS-485 的實體線路，兩台機器硬體上連通了，但它們需要一種「語言」來溝通。這就是 Modbus 登場的時候了。

1. Modbus RTU (基於序列埠)

Modbus 是 1979 年由 Modicon 公司發明的公開通訊協定，至今仍是工業界的絕對主流（因為簡單、免費且可靠）。Modbus 採用 Master-Slave (主從架構)：

  • 網路上只能有一個 Master（通常是 PLC 或電腦）。
  • Master 發出請求 (Request)，對應的 Slave (感測器/機台) 收到後回覆 (Response)。
  • Slave 永遠不會主動發送資料（不支援 Pub/Sub）。

資料結構： Modbus 的核心概念是「暫存器 (Registers)」。資料分為四種類型：

  1. Coils: 可讀可寫的布林值 (例如：控制馬達開關)。
  2. Discrete Inputs: 唯讀的布林值 (例如：門是否關閉的感測器)。
  3. Input Registers: 唯讀的 16-bit 數值 (例如：目前的溫度值)。
  4. Holding Registers: 可讀可寫的 16-bit 數值 (例如：設定冷氣的目標溫度)。

Modbus RTU 是將上述資料封裝成二進位 (Binary) 格式，並加上 CRC 校驗碼，然後透過 RS-485 或 RS-232 發送出去。

2. Modbus TCP (基於乙太網路)

隨著網路普及，工業界希望把舊的 Modbus 協定搬到 TCP/IP 上。於是就有了 Modbus TCP。

  • 架構： 將 Master/Slave 改稱為 Client/Server。
  • 底層： 跑在標準的乙太網路上，預設 Port 為 502。
  • 格式變化： 移除了 RTU 的 CRC 校驗碼（因為 TCP 已經有 checksum 保證正確性），並在封包最前面加上了 7 個 bytes 的 MBAP Header (Modbus Application Protocol Header)。

第三層：軟體交換層 (Middleware / Software Layer) 系統整合

當我們把底層硬體 (PLC、變頻器、各廠牌感測器) 透過 Modbus 接上網路後，上位機 (SCADA 系統、MES 系統或寫 Python 收集資料的你) 會面臨一個大問題：每家廠商的暫存器定義都不一樣！

三菱的 PLC 和西門子的 PLC，讀取溫度的方式完全不同。為了解決這種軟體層面的大亂鬥，微軟與工業界陸續推出了 DDE 與 OPC 標準。

1. DDE (Dynamic Data Exchange)

在早期的 Windows (Windows 3.0/95 時代)，微軟推出了一種讓不同應用程式之間共享資料的機制，稱為 DDE。許多早期的工業軟體利用 DDE 將 PLC 的資料直接送到 Excel 儲存格裡顯示。

  • 原理： 基於 Windows 訊息機制的 IPC (進程間通訊)。它使用 Application|Topic!Item 的格式來定位資料。
  • 缺點： 效能極差，經常造成系統當機；且不具備網路擴展性（雖然有 NetDDE，但也已被淘汰）。目前 DDE 已是歷史文物，在現代工業系統中幾乎被全面棄用。

2. OPC DA (Data Access) - 經典 OPC

為了取代難用的 DDE，1996 年成立了 OPC 基金會，推出了 OPC 規範（全名 OLE for Process Control）。OPC DA 是一個中介軟體標準：

底層機台製造商（如西門子）只負責寫一個 OPC Server 軟體。這個 Server 往下透過 Modbus 或專有協定跟硬體溝通，往上則暴露統一的 Windows COM/DCOM 介面。這樣，SCADA 軟體只要實作 OPC Client，就能統一讀取所有廠牌的設備，達到了「隨插即用」。

  • 架構： 基於微軟的 COM/DCOM 技術。
  • 致命傷：
    1. 綁死 Windows：因為依賴 COM/DCOM，所以無法在 Linux 或嵌入式設備上運行。
    2. 網路設定噩夢：透過 DCOM 進行跨網段通訊時，需要設定繁瑣的 Windows 登錄檔與防火牆，被工程師戲稱為「DCOM 地獄」。
    3. 安全性極低：缺乏現代的加密與憑證機制。

3. OPC UA (Unified Architecture) - 現代工業 4.0 標準

為了徹底解決 OPC DA 綁定 Windows 與安全性差的問題，OPC 基金會於 2008 年推出了全新架構：OPC UA。這也是目前工業物聯網 (IIoT) 的黃金標準。

  • 跨平台 (Platform Independent)： 徹底拋棄了 COM/DCOM。底層採用標準的 TCP/IP (二進位 opc.tcp) 或是 HTTP/SOAP，完美支援 Linux、macOS、Docker 甚至微型感測器單晶片。
  • 強大的資訊模型 (Information Model)： OPC DA 只能傳遞「標籤 (Tag)」和「值 (Value)」。而 OPC UA 採用物件導向 (Object-Oriented)，可以定義一台「馬達」，這台馬達底下包含溫度、轉速等多個節點，資料具有結構與語義。
  • 現代化安全性 (Security)： 內建 X.509 憑證雙向認證，傳輸過程支援 AES 加密與簽章，符合現代 IT 資安標準。
  • 多種通訊模式： 除了傳統的 Client/Server 模式外，還新增了 Pub/Sub (發布/訂閱) 模式，非常適合整合 MQTT 與雲端大數據分析。

總結與技術演進圖

工業通訊的發展史，就是一部「從實體線路走向網路化，從封閉系統走向跨平台與物件化」的歷史。

技術分層 舊時代 (過去) 現代 (現在與未來) 核心特徵差異
硬體實體層 RS-232 / RS-485 Ethernet (RJ45, 光纖) 從點對點、半雙工序列埠，演進為高速、全雙工的 IP 網路。
資料協定層 Modbus RTU Modbus TCP 將暫存器讀寫指令封裝進 TCP/IP 封包中。
軟體交換層 DDE / OPC DA OPC UA 從綁死 Windows COM/DCOM、無加密，演進為跨平台、物件化、高資安防護的架構。

對於軟體工程師來說，如果你的任務是要去工廠「撈資料」：

  1. 如果設備很新，請直接詢問是否有提供 OPC UA Server 或支援 MQTT，你可以輕鬆用 Python (asyncua) 或 Node.js 接接 API 就搞定。
  2. 如果設備是傳統 PLC，大概率會支援 Modbus TCP，你可以使用 pymodbus 透過 TCP/IP 去讀取特定 Register。
  3. 如果是超級老舊的感測器，你可能需要準備一條 USB 轉 RS485 轉換線，親手處理 Baud rate 與 Modbus RTU 的二進位解析了。
