01. API 本質與分散式系統的演進脈絡

在單一單體系統（Monolith）中，元件間的協作是透過 程序內呼叫（In-Process Function Call） 實現的。呼叫者將參數推入 CPU 堆疊（Stack）、發出 CALL 組合語言指令跳躍至記憶體位址，並由 CPU 暫存器（如 RAX/EAX）讀取回傳值。此時的延遲僅在數十至數百奈秒（Nanoseconds, ns）等級，記憶體空間共享，資料型別完全對齊。

然而，當系統規模擴展為微服務（Microservices）與多租戶雲端架構時，元件被拆分至獨立實體機、容器與不同可用區（Availability Zones），溝通轉變為透過不可靠的實體網路進行。軟體工程師必須直面著名的「分散式計算 8 大謬論（Fallacies of Distributed Computing）」：

🌐 網路是可靠的 (Network is reliable)

封包隨時可能遺失、重複或亂序。API 必須設計重試機制、超時熔斷（Circuit Breaker）與冪等性防護。

⏱️ 延遲為零 (Latency is zero)

光纖傳輸受物理極限束縛，跨資料中心 RTT 高達數十毫秒。減少網路往返（Round Trips）成為架構首要目標。

📦 頻寬是無限的 (Bandwidth is infinite)

行動網路與高併發連線下，JSON 冗餘字串會造成頻寬擁塞與 CPU 序列化/反序列化（SerDe）瓶頸。

🛡️ 網路是安全的 (Network is secure)

內網不再可信（Zero Trust 零信任架構），每條 API 管道都需 mTLS 加密、強固的身分憑證與細粒度授權。

從早期過度複雜的 RPC 協議（CORBA, DCOM, SOAP / XML-RPC），到 2000 年 Roy Fielding 博士提出資源導向的 REST，再到因應行動裝置複合查詢的 GraphQL、微服務高併發內網專用的 gRPC，以及現代生成式 AI 大模型不可或缺的 SSE 流式輸出，API 的演進本質上是一部「在抽象靈活性、傳輸開銷、強型別契約與網路延遲之間尋求最佳平衡」的博弈史。

02. RESTful 架構深潛與 Richardson 成熟度模型 (RMM)

REST (Representational State Transfer，表現層狀態轉移) 並非通訊協定，而是一套架構約束風格（Architectural Style）。由 Leonard Richardson 提出的 Richardson Maturity Model (RMM) 將 API 符合 REST 哲學的程度劃分為 4 個等級：

等級 (Level) 核心概念 設計方式範例 特徵與評價
Level 0 The Swamp of POX POST /api/service (Body: {"action":"getUser", "id":10}) 單一端點、單一 HTTP POST 動詞，本質是偽裝成 Web 的 RPC。
Level 1 Resources (獨立資源) POST /users/10, POST /orders/88 引入複數著名資源 URI，但仍未規範 HTTP 動詞（多數全用 POST）。
Level 2 HTTP Verbs & Status Codes GET /users/10, DELETE /orders/88 (返回 204 No Content) 絕大多數成熟生產環境 API 的標準水準，嚴格遵守 HTTP RFC 語意。
Level 3 HATEOAS (超媒體即狀態引擎) 回傳資料包含 _links 導航下一動態可用動作（如 cancel, pay） 客戶端無需硬編碼路徑，如同人類在網頁點擊超連結，但在實務上實作成本極高。

HTTP 動詞安全性與冪等性 (Safety & Idempotence)

根據 RFC 9110 (HTTP Semantics)，理解 HTTP 動詞的數理性質是設計高可靠 API 的基本功：

  • 安全性 (Safe)： 該請求不會改變伺服器的資源狀態，只進行讀取。範例：GET, HEAD, OPTIONS。
  • 冪等性 (Idempotent)： 執行一次與執行 $N$ 次 ($N \ge 1$)，對伺服器產生的副作用（Side Effects）完全相同。 $$\text{Effect}(f(x)) = \text{Effect}(f(f(x))) = \cdots = \text{Effect}(f^N(x))$$
HTTP Method Safe (安全) Idempotent (冪等) 語意用途 典型成功回應狀態碼
GET YES YES 讀取資源，不得造成商業資料變更 200 OK
POST NO NO 建立子資源、觸發業務程序（如發動扣款） 201 Created
PUT NO YES 全量覆蓋資源（若不存在則建立，存在則整筆替換） 200 OK / 204 No Content
PATCH NO 條件冪等 局部更新（JSON Merge Patch 冪等；若為陣列 append 則非冪等） 200 OK / 204 No Content
DELETE NO YES 刪除資源（第二次執行刪除回傳 404，但資源狀態維持已刪除） 200 OK / 204 No Content

實戰：生產級 Idempotency-Key 冪等防重複機制

在網路不穩定的環境下（如行動端弱網扣款），客戶端發送 POST /orders 後可能因為逾時（Timeout）未收到回應，此時重試請求極易引發重複扣款。業界標準做法是透過 HTTP Header 攜帶 Idempotency-Key: <UUIDv4>：

# 基於 Redis 分散式鎖的 API 冪等中間件範例 (Python FastApi / Redis)
import uuid, json
from fastapi import FastAPI, Request, HTTPException, status
import redis

r = redis.Redis(host='localhost', port=6379, decode_responses=True)

async def idempotency_middleware(request: Request, call_next):
    if request.method not in ["POST", "PATCH"]:
        return await call_next(request)

    idemp_key = request.headers.get("Idempotency-Key")
    if not idemp_key:
        return await call_next(request) # 或依策略強制要求 Header

    redis_key = f"idemp:{idemp_key}"
    
    # 嘗試以 SETNX (Set if Not Exists) 搶佔鎖，過期時間 120 秒
    acquired = r.set(redis_key, json.dumps({"status": "IN_PROGRESS"}), nx=True, ex=120)
    
    if not acquired:
        cached = json.loads(r.get(redis_key))
        if cached.get("status") == "IN_PROGRESS":
            raise HTTPException(status_code=status.HTTP_409_CONFLICT, detail="請求處理中，請勿重複提交")
        # 直接回傳已處理成功的快取結果，免除重複扣款業務邏輯
        return Response(content=cached["body"], status_code=cached["status_code"], media_type="application/json")

    # 執行真實業務邏輯
    response = await call_next(request)
    body = [section async for section in response.body_iterator]
    
    # 業務完成後將回應結果存入 Redis
    r.set(redis_key, json.dumps({"status": "DONE", "status_code": response.status_code, "body": body[0].decode()}), ex=86400)
    return Response(content=body[0], status_code=response.status_code, headers=dict(response.headers))

03. GraphQL 原理、AST 執行與 N+1 查詢終極破解

RESTful 在行動時代面臨兩大天然缺陷：Over-fetching（過度獲取）（例如行動端只需要使用者頭像與暱稱，REST 卻回傳 50 個包含地址、權限的欄位，浪費頻寬）；以及 Under-fetching（獲取不足）（需要先呼叫 /users，再根據回傳呼叫 /posts，再呼叫 /comments，引發瀑布流網路往返）。

Meta 於 2015 年開源的 GraphQL 採用「宣告式資料獲取（Declarative Data Fetching）」哲學。客戶端透過單一端點（通常為 POST /graphql）提交查詢文件，精確描述所需結構：

GraphQL 引擎底層運作流程

  1. 語彙與語法分析 (Lexing & Parsing)： 將 Query 字串解析為 AST (Abstract Syntax Tree，抽象語法樹)。
  2. 型別驗證 (Validation)： 比對 Schema 定義，檢查欄位名稱、參數型別是否存在且符合契約。
  3. 遞迴解析執行 (Execution via Resolvers)： 遍歷 AST 節點，由根層級（Query/Mutation）向下觸發各欄位的 Resolver 函數。

致命痛點：N+1 查詢問題與 DataLoader 解法

GraphQL 的彈性帶來了嚴重的資料庫效能隱患——$N+1$ 查詢問題。假設我們查詢 10 篇文章及其作者：

query {
  posts(limit: 10) { # 執行 1 次查詢: SELECT * FROM posts LIMIT 10
    title
    author {         # 針對每一篇 post 觸發獨立 Resolver，共執行 10 次查詢！
      name           # SELECT * FROM users WHERE id = post.author_id
    }
  }
}

此時總共發送了 $1 + 10 = 11$ 次 SQL 查詢。若 limit 是 100，就會爆發 101 次資料庫存取，瞬間耗盡連線池。

DataLoader 解決方案： 利用 Node.js 或各語言的非同步 Event Loop 微任務隊列（如 process.nextTick 或 Promise microtask），在同一迴圈 Tick 內將分散的單筆 ID 收集成陣列，合併為單次批次查詢：

$$\text{Original: } 10 \times (\text{SELECT FROM users WHERE id} = ?) \implies \text{DataLoader: } 1 \times (\text{SELECT FROM users WHERE id IN } (1, 2, \dots, 10))$$ 
// Node.js DataLoader 實踐範例
const DataLoader = require('dataloader');

// 批次加載函數：傳入 ID 陣列，必須回傳順序完全對應的資料 Promise 陣列
const userLoader = new DataLoader(async (userIds) => {
  const users = await db.users.findMany({
    where: { id: { in: userIds } }
  });
  // 必須依照 userIds 的順序回傳，若查無資料則對應為 null
  const userMap = new Map(users.map(u => [u.id, u]));
  return userIds.map(id => userMap.get(id) || null);
});

// GraphQL Resolver:
const resolvers = {
  Post: {
    author: (post, args, context) => {
      // 這裡不會立即發送 SQL，而是註冊進 DataLoader 批次隊列
      return context.userLoader.load(post.authorId);
    }
  }
};

04. gRPC、HTTP/2 多工與 Protobuf 二進位序列化

在大型分散式微服務架構中，內部服務間的通訊量動輒每秒數十萬次。若仍使用 REST + JSON，系統會承受巨大代價：文字格式 JSON 體積龐大、需耗費可觀 CPU 進行字串編解碼（SerDe），且 HTTP/1.1 受限於連線隊頭阻塞（Head-of-Line Blocking）。

Google 推出的 gRPC 結合了 HTTP/2 傳輸層與 Protocol Buffers (Protobuf) 二進位序列化，成為微服務通訊的黃金標準：

1. HTTP/2 傳輸架構革新

  • 二進位分訊框 (Binary Framing)： HTTP/2 不再傳輸純文字 ASCII，而是將訊息分割為二進位的 HEADERS 與 DATA 訊框（Frame）。
  • 多工串流複用 (Multiplexing)： 在單一 TCP 實體連線上，可並行交錯傳輸多個雙向 Stream，徹底消除連線建立的 3-Way Handshake 與隊頭阻塞。
  • HPACK 標頭壓縮： 通訊雙方各自維護一份靜態與動態字典，重複的 Header（如 User-Agent, Authorization）僅需傳輸索引數字（如數個位元組），節省高達 85% 標頭頻寬。

2. Protocol Buffers (proto3) 為什麼比 JSON 快且小？

Protobuf 捨棄了 JSON 每次傳輸都包含欄位名稱（如 "username": "robert"）的冗餘做法，採用 Tag-Length-Value (TLV) 架構與數理壓縮編碼：

🔢 Varint (可變長整數編碼)

傳統 32-bit 整數固定佔 4 Bytes。Varint 利用每個 Byte 的第 8 位（MSB）作為延續標記（Continuation Bit），僅用低 7 位儲存數值。對於較小的數（如 1 ~ 127），僅需 1 個 Byte 即可表示！

📐 ZigZag 負數映射

在補數運算中，負數（如 -1）高位全為 1，Varint 會膨脹為 10 Bytes。Protobuf 透過 ZigZag 演算法將有符號整數映射為無符號正數：$0 \to 0, -1 \to 1, 1 \to 2, -2 \to 3$： $$\text{ZigZag}(n) = (n \ll 1) \oplus (n \gg 31)$$ 讓小的負數也能享有 1~2 Bytes 的極小體積。

// 定义 service 与 message 契约 (order.proto)
syntax = "proto3";
package ecommerce.v1;

service OrderService {
  rpc CreateOrder (CreateOrderRequest) returns (CreateOrderResponse);
  rpc StreamOrderStatus (StreamOrderRequest) returns (stream OrderStatusUpdate); // 伺服器長串流
}

message CreateOrderRequest {
  string user_id = 1;      // Tag 1 (Wire Type 2: Length-delimited)
  double total_amount = 2;  // Tag 2 (Wire Type 1: 64-bit)
  repeated string item_ids = 3;
}

05. 即時通訊對決：WebSocket vs SSE (AI 串流)

在即時互動（Real-time Communication）領域，工程師常常面臨 WebSocket 與 Server-Sent Events (SSE) 的選型分歧：

為什麼現代 AI 大模型（ChatGPT / Claude）全都採用 SSE 而非 WebSocket？

在大語言模型（LLM）的推理場景中，使用者發送一個 Prompt 之後，伺服器開始透過自回歸（Autoregressive）模式一個 Token 一個 Token 輸出文字。許多人下意識認為「即時通訊就該用 WebSocket」，但實際上主流大廠（OpenAI, Anthropic, Google）無一例外採用 SSE：

比較面向 WebSocket Server-Sent Events (SSE) AI 串流情境抉擇理由
通訊方向 全雙工 (Full-Duplex，雙向即時發送) 單向推播 (Server to Client) LLM 推理是標準的「單次請求，長篇單向流式回傳」，無需雙向全雙工。
協定基礎 自獨立 TCP 協定（ws://, wss://）需 Upgrade 握手 標準 HTTP/1.1 或 HTTP/2 (text/event-stream) SSE 是原生 HTTP，天然相容現有 API Gateway、WAF、CDN 與 Nginx 負載平衡。
中斷自動重連 需前端手動以 JavaScript 輪詢重連 瀏覽器原生 EventSource 自動重連 SSE 支援 Last-Event-ID 標頭，斷線重連能無縫接續 Token，不漏字。
多工與連線開銷 需維護 Stateful 連線狀態與 Ping/Pong 心跳 在 HTTP/2 上可多路複用單一 TCP 連線 HTTP/2 SSE 資源消耗極低，防火牆不會隨意掐斷連線。

06. 事件驅動架構 (EDA) 與 Webhook 防禦

傳統 API 由客戶端定期發送輪詢（Polling）詢問狀態，造成 95% 以上的請求是無效空轉。Webhook（反向 API） 是事件驅動架構（EDA）中跨系統整合的重要手段：當第三方系統（如 Stripe 扣款、GitHub Push）事件發生時，主動以 HTTP POST 呼叫接收方的端點。

生產級 Webhook 必備防護機制

  1. HMAC-SHA256 簽名防偽： 防止冒牌攻擊者偽造請求發起非法充值。發送方利用雙方約定的 Secret 對請求 Body 計算雜湊值，附在 Header（如 X-Signature: sha256=...），接收方以 Constant-Time 比較防止時序攻擊（Timing Attack）。
  2. 時間戳防重放攻擊 (Replay Attack Prevention)： 在簽名中納入時間戳（如 X-Timestamp: 1729252800），接收端若發現請求時間與伺服器目前時間相差超過 5 分鐘，即判定無效丟棄。
  3. 指數退避重試與死信隊列 (DLQ)： 接收端若發生當機或回傳 5xx，發送端需採取指數退避（Exponential Backoff with Jitter）： $$T_{\text{wait}} = \min(T_{\max}, T_0 \times 2^{\text{attempt}}) \pm \text{RandomJitter}$$ 重試超過上限後推入死信隊列（DLQ）供人工審查。

07. API 閘道、四大多工限流演算法與版本治理

在微服務入口處，API Gateway（如 Kong, Envoy, Traefik, APISIX） 統一承擔路由、SSL 卸載、身分驗證與流量限制（Rate Limiting），保護後端資料庫免於雪崩：

四大限流演算法深度對比

⏱️ 固定視窗計數器 (Fixed Window)

在固定週期（如 1 分鐘）內限制計數。缺點是臨界點突發問題：若前一分鐘最後 5 秒與下一分鐘前 5 秒各來 100 次請求，在 10 秒內會爆發 200 次流量，超出系統極限。

📜 滑動視窗日誌 (Sliding Log)

將每個請求的精確時間戳記錄在 Redis Sorted Set (ZSET)。計算過去 60 秒內的請求總數。優點是絕對精準，但高併發時記憶體膨脹嚴重。

🌊 漏桶演算法 (Leaky Bucket)

將突發請求倒入固定容量的桶中，以恆定不變的速率從桶底流出處理。能達到絕對的流量平滑，但無法處理正常突發流量，延遲較高。

🪙 權杖桶演算法 (Token Bucket)

業界最廣泛採用！系統以恆定速率向容量為 $C$ 的桶內放入權杖（Tokens）。請求需消耗權杖，桶滿則溢出。兼具允許安全範圍內的短暫突發流量，又限制長期平均速率。

08. API 安全實踐與 OWASP API Security Top 10

API 是現代資安攻擊最嚴重的重災區。OWASP 發布的 API Security Top 10 中，最危險的漏洞常年盤踞榜首：

1. BOLA (Broken Object Level Authorization，物件級授權無效)

俗稱 IDOR（不安全的直接物件引用）。使用者登入成功後，攻擊者惡意將請求中的 ID 改為他人 ID（如 GET /api/v1/invoices/9999）。若後端僅檢查「此人是否登入」，而沒有驗證「該使用者是否有權存取 ID 為 9999 的帳單」，他人私密隱私即告外洩！

2. 現代權杖演進：JWT vs PASETO

傳統 JWT 採用 JOSE 規範，允許在 Header 中自訂演算法（如 "alg": "none" 或 "alg": "HS256"）。攻擊者曾多次利用弱點將非對稱 RS256 降級為對稱 HS256，利用公開金鑰冒簽 Token。PASETO (Platform-Agnostic Security Tokens) 採用免配置密碼學套件（No Algorithm Negotiation），徹底封堵了演算法降級漏洞。
