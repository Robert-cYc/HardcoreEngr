PyInstaller 完全操作指南：安裝、--onefile 與 --onedir 核心指令詳解、資源打包、動態 Hook 與除錯避坑手冊

PyInstaller Python 打包 exe 製作 CLI 指令 動態 Hook 多行程避坑 代碼安全防護 GitHub Actions 開發工具 教學
🎯 TL;DR 速覽精要：
• PyInstaller 的本質： 一款將 Python 腳本、CPython 直譯器運行庫（DLL/so/dylib）、標準庫與第三方依賴整合為獨立二進位檔（Windows .exe、macOS App、Linux binary）的打包工具，目標電腦無需安裝 Python 即可直接執行。
• 模式核心差異：
  - --onefile (-F)：打包為單一獨立執行檔。分發極簡，但啟動時會先解壓至臨時目錄（冷啟動慢），適合交付給終端一般使用者的獨立工具。
  - --onedir (-D，預設)：打包為包含執行檔與依賴函式庫的目錄。啟動秒開、排錯便利、支援手動替換靜態檔案，適合大型專案或搭配 Inno Setup 安裝包。
• 四大致命踩坑點：
  1. 靜態資源存取：打包後的外部檔案需透過 sys._MEIPASS 動態計算解壓路徑，絕不能寫死相對路徑！
  2. Windows 多行程（Multiprocessing）：在 Windows 下未加 multiprocessing.freeze_support() 會引發無限複製的進程炸彈（Fork Bomb）直接當機！
  3. 現代套件 Metadata 缺失：Python 3.8+ 廣泛採用 importlib.metadata，必須使用 copy_metadata 或 --collect-all 補齊詮釋資料，否則執行期噴 PackageNotFoundError。
  4. 反編譯迷思：PyInstaller 不是加密器！5 秒內即可被 pyinstxtractor + pycdc 還原原始碼。若要保護商用專利邏輯，必須搭配 Cython 編譯為 .pyd 或使用 PyArmor 混淆。

一、什麼是 PyInstaller？底層運作原理剖析

在 Python 開發中，交付軟體給非技術使用者往往是個惡夢：目標電腦通常沒有安裝 Python，也沒有設定好 PATH，即便安裝了也可能因為 pip 依賴衝突、C++ 運行庫缺失或版本不合導致程式無法啟動。PyInstaller 正是為了解決此痛點而生的高成熟度業界標準方案。

很多初學者誤以為 PyInstaller 是「將 Python 代碼編譯成 C++ 或 CPU 機器碼的編譯器」，這是一個根本性的誤解。PyInstaller 實際上執行的是一套嚴密的「環境收集、打包與引導（Bootstrapping）」自動化流程：

  1. 靜態抽象語法樹分析（AST Analysis）： PyInstaller 從你指定的入口腳本（例如 main.py）開始，解析整份代碼中的所有 import、from ... import ... 語句，建立遞迴的模組依賴關係圖（Import Dependency Graph）。
  2. 收集 CPython 執行期核心與二進位擴展： 它會從你當前操作系統的 Python 環境中，完整抽取對應版本的 Python 直譯器核心動態庫（如 Windows 下的 python311.dll、Linux 的 libpython3.so）、所有涉及的 C 擴展庫（.pyd 檔，如 socket、hashlib、numpy 等）以及相關的 C 運行時庫（如 VCRUNTIME140.dll）。
  3. 字節碼編譯與歸檔（PYZ Archive）： 它將所有的純 Python 模組（.py）先行編譯為字節碼（.pyc），並壓縮打包成一個名為 PYZ 的內部 zip 封裝包。
  4. 注入引導程式（C Bootloader）： PyInstaller 為產物注入一段用 C 語言編寫的高效引導程式。當使用者雙擊最終的 .exe 時，是 Bootloader 最先接管作業系統進程：它在記憶體中（或臨時目錄中）初始化 Python 虛擬機環境、設定好 sys.path，最後引導 CPython 直譯器載入並執行你的入口腳本。

二、PyInstaller 安裝與環境準備（含 venv / uv 隔離實踐）

1. 標準安裝 (pip)

在終端機中直接使用 pip 安裝最新穩定版：

# 安裝最新穩定版 PyInstaller
pip install pyinstaller

# 驗證安裝與查看版本
pyinstaller --version

2. 升級或安裝 GitHub 最新開發版

若使用的是剛發布的 Python 新版（例如 Python 3.12+ / 3.13），官方 PyInstaller 穩定版可能尚未完全適配新語法樹，建議更新至開發分支：

# 升級現有穩定版本
pip install --upgrade pyinstaller

# 安裝 GitHub 最新開發分支以獲得最新特性修復
pip install https://github.com/pyinstaller/pyinstaller/tarball/develop

3. 核心規範：務必在獨立虛擬環境中打包！

許多人第一次打包時經常崩潰：「我就寫了個 20 行的爬蟲腳本，為什麼打包出來的 exe 高達 400MB？啟動還要卡 10 秒？！」

根本原因： 你直接在全域 Python 環境（或 Anaconda Base 環境）中執行打包！PyInstaller 的靜態掃描器非常盡責，它會將全域環境中所有被間接掃描到或觸發 hook 的龐大科學計算套件（如 pandas、torch、scipy、matplotlib）全部一股腦捲入 exe 中。

💡 方案 A：標準 Python venv

# 1. 建立乾淨環境
python -m venv .venv

# 2. 啟動環境 (Windows PowerShell)
.\.venv\Scripts\Activate.ps1

# 3. 僅安裝該專案真正需要的套件
pip install requests pyinstaller

⚡ 方案 B：使用新一代極速工具 uv

# 1. 使用 uv 建立環境
uv venv

# 2. 啟動環境 (Windows)
.venv\Scripts\activate

# 3. 秒級安裝乾淨依賴
uv pip install requests pyinstaller

三、核心指令與參數詳解速查手冊

PyInstaller 提供了豐富的命令列參數。熟練掌握以下旗標，即可涵蓋生產環境中 98% 的打包需求：

參數選項 簡寫 功能深度解析 實務適用情境
--onefile -F 將所有程式碼、依賴庫與直譯器打包進單一獨立可執行檔。 向客戶分發免安裝的小工具、CLI 程式。
--onedir -D 產出包含 exe 與諸多依賴 DLL 的資料夾目錄（預設行為）。 大型桌面軟體、頻繁啟動專案、搭配安裝程式。
--windowed / --noconsole -w 關閉主控台黑框，啟動時不彈出 CMD 視窗。 PyQt、Tkinter、wxPython 等純桌面 GUI 程式。
--console / --nowindowed -c 保留主控台視窗（預設選項），標準輸出印在黑框中。 終端工具、排錯與即時觀測 print / logging。
--icon=<PATH> -i 指定可執行檔圖示（Windows 需 .ico，macOS 需 .icns）。 客製化應用程式圖示與品牌識別。
--name=<NAME> -n 自訂輸出的 exe / 目錄檔名（預設為入口腳本名）。 規範建置產物命名（如 SuperTool-v1.0）。
--add-data <SRC;DEST> - 封裝非程式碼靜態資源（Windows 用 ;，Unix 用 :）。 打包圖片、HTML/CSS 模板、JSON/YAML 設定檔。
--add-binary <SRC;DEST> - 封裝外部原生二進位函式庫（DLL、.so、.dylib）。 調用 C/C++ 編譯的原生共享庫或驅動。
--hidden-import=<MOD> - 手動宣告靜態掃描漏掉的隱藏動態引入模組。 __import__()、importlib 動態載入的套件。
--collect-all <PKG> - 終極神器：一鍵收集指定套件的所有子模組、靜態數據與二進位檔。 解決 Playwright、Torch、Transformers 打包缺失。
--copy-metadata <PKG> - 複製指定套件的 dist-info 詮釋資料。 解決 Python 3.8+ PackageNotFoundError 崩潰。
--exclude-module=<MOD> - 明確排除無關的龐大函式庫。 產物極致瘦身（剔除 Tkinter、Matplotlib 等）。
--clean - 建置前強制清理前次的 build 快取與暫存檔。 設定大幅修改或更換依賴後的乾淨建置。
--uac-admin - 在 Windows PE 檔案中內嵌 UAC 資訊，啟動時強制要求系統管理員權限。 修改註冊表、寫入系統目錄、網路驅動檢測工具。
--upx-dir=<DIR> - 指定 UPX 可執行檔壓縮程式的路徑以自動壓縮二進位檔。 顯著縮減 exe 檔案體積（最高可節省 40%~60%）。
--upx-exclude=<DLL> - 指定禁止被 UPX 壓縮的 DLL 檔案（防止壓縮損壞）。 避免 vcruntime140.dll 或 Qt 核心 DLL 壓縮後崩潰。
--debug=all - 開啟 Bootloader 與依賴載入的所有詳細除錯日誌。 排查底層 DLL 遺失與動態連結載入失敗。

四、--onefile vs. --onedir 核心架構差異與選型決策

📦 --onefile (單一執行檔模式)

輸出結果： 僅產出單一一個乾淨的 myapp.exe。

運作機制： 當雙擊執行時，Bootloader 會在系統暫存目錄（Windows 為 %TEMP%/_MEIxxxxxx）開闢一個隨機臨時資料夾，將壓縮在 PE 尾部內的所有依賴 DLL、.pyd 與靜態資源全數解壓到硬碟，然後才啟動直譯器。程式結束退出時，Bootloader 再非同步清理該臨時目錄。

優勢： 交付極簡，客戶只需點擊一個檔案即可運行。

劣勢： 每次啟動有明顯解壓開銷（冷啟動耗時 1~5 秒）；異常終止可能殘留垃圾暫存；讀取外部檔案需透過 sys._MEIPASS 處理。

📁 --onedir (目錄模式 - 預設)

輸出結果： 產出包含 myapp.exe 與數十個依賴檔、資料夾的 dist/myapp/ 目錄。

運作機制： myapp.exe 直接以自身所在目錄為基準載入旁邊的 DLL 與庫，完全沒有解壓過程。

優勢： 啟動秒開，效能毫無折損；排查缺少哪個 DLL 或模組一目了然；更換設定檔或圖片直接替換即可，無需重新編譯整份專案。

劣勢： 檔案零碎分散，發布時通常需壓縮為 ZIP 或使用 Inno Setup、NSIS 封裝為標準 Windows 安裝包（Setup.exe）。

五、完整實戰操作教學：從零打包一個真實應用

我們以一個包含 config.json 設定檔、assets/logo.png 靜態資產與 requests 網路請求的標準應用為例：

1. 專案目錄結構

my_app/
├── assets/
│   └── logo.png
├── config.json
└── main.py

2. 執行打包指令

在 Windows 下打包為單一執行檔，包含外部檔案與自訂圖示：

# Windows 終端機執行（路徑分隔請使用分號 ;）
pyinstaller --onefile \
  --windowed \
  --name="StockMonitor" \
  --icon="app.ico" \
  --add-data="config.json;." \
  --add-data="assets/logo.png;assets" \
  --clean \
  main.py

# macOS / Linux 終端機執行（路徑分隔請使用冒號 :）
pyinstaller --onefile \
  --name="StockMonitor" \
  --add-data="config.json:." \
  --add-data="assets/logo.png:assets" \
  --clean \
  main.py

3. 建置產物目錄拆解

  • dist/：最終可執行檔或資料夾（交付給使用者的最終產物）。
  • build/：編譯過程中的依賴解析樹、編譯中繼檔與 warn 日誌。打包完成後隨時可以手動刪除。
  • StockMonitor.spec：PyInstaller 根據指令產生的完整規格設定檔。強烈建議將此檔案加入 Git 版本控管，日後直接針對此 spec 檔建置！

六、四大路徑變數對照手冊（Path Cheat Sheet）

很多 Python 工程師在打包後最常遇到的崩潰，就是「找不到檔案」或「程式重開後設定全部被洗掉重置」。這是因為沒有搞清楚靜態唯讀資產與持久化使用者資料的路徑區隔：

路徑變數 未打包 (本機開發時) --onefile 打包後 --onedir 打包後 適用情境與存取特性
sys._MEIPASS 不存在（觸發 AttributeError） C:\Users\...\AppData\Local\Temp\_MEIxxxxxx C:\...\dist\myapp (或同 exe 目錄) 唯讀靜態資產（圖片、內建模板、內建預設設定）。絕對不可寫入資料，因為 onefile 退出時暫存目錄會被銷毀！
os.path.dirname(sys.executable) Python 直譯器路徑（如 C:\Python311） exe 本體所在的真實目錄 exe 本體所在的真實目錄 持久化檔案儲存：適合放置使用者可手動編輯的 config.yaml、產出的 output/ 檔案、持久化 SQLite 資料庫。
__file__ 原始碼 main.py 的絕對路徑 指向 _MEIPASS/main.pyc 的暫存檔名 指向 dist/myapp/main.pyc 僅能代表模組本身的字節碼位置，不可用作使用者資料儲存定位。
os.getcwd() 啟動終端機所在的目錄 使用者啟動程式當下的當前目錄 使用者啟動程式當下的當前目錄 極不可靠！若使用者透過桌面捷徑、Windows 工作排程器或右鍵選單開啟，工作目錄常被重設為 C:\Windows\System32！

生產級雙軌路徑管理器程式碼模板

請將以下模組加入你的專案，它能自動區分「唯讀打包資源」與「持久化可寫入目錄」：

# path_manager.py
import sys
import os
from pathlib import Path

def get_bundle_resource(relative_path: str) -> str:
    """
    取得打包內嵌的唯讀資源路徑（圖片、UI 檔案、預設設定）
    相容：本機開發環境 與 PyInstaller (--onefile / --onedir)
    """
    if getattr(sys, 'frozen', False) and hasattr(sys, '_MEIPASS'):
        # PyInstaller --onefile 解壓縮臨時目錄
        base_path = sys._MEIPASS
    else:
        # 本地開發時，以當前專案根目錄為準
        base_path = os.path.dirname(os.path.abspath(__file__))
    
    return os.path.normpath(os.path.join(base_path, relative_path))

def get_writable_app_dir(app_name: str = "MyAwesomeApp") -> Path:
    """
    取得安全可寫入的使用者設定/資料庫儲存目錄
    Windows: %APPDATA%\MyAwesomeApp
    macOS: ~/Library/Application Support/MyAwesomeApp
    Linux: ~/.config/MyAwesomeApp
    """
    if sys.platform == "win32":
        base = os.getenv("APPDATA") or os.path.expanduser("~")
    elif sys.platform == "darwin":
        base = os.path.expanduser("~/Library/Application Support")
    else:
        base = os.getenv("XDG_CONFIG_HOME") or os.path.expanduser("~/.config")
        
    app_dir = Path(base) / app_name
    app_dir.mkdir(parents=True, exist_ok=True)
    return app_dir

def get_exe_dir() -> Path:
    """取得 exe 執行檔所在的實體資料夾（適合放免安裝隨身碟的外部配置檔）"""
    if getattr(sys, 'frozen', False):
        return Path(sys.executable).resolve().parent
    return Path(__file__).resolve().parent

七、進階技巧：使用 .spec 規格檔優雅管理複雜配置

當專案變得複雜、外部依賴包含十幾個資料夾與幾十個隱藏導入時，在終端機拼湊幾百個字元的 CLI 命令既容易出錯又難以重複。此時直接編輯 .spec 檔才是專業工程師的做法：

# -*- mode: python ; coding: utf-8 -*-
# StockMonitor.spec
import sys
from PyInstaller.utils.hooks import copy_metadata, collect_data_files

# 提高遞迴深度，防止巨型套件（如 torch / pandas）解析時溢出
sys.setrecursionlimit(5000)

block_cipher = None

# 1. 集中管理靜態資源 [(來源硬碟路徑, 打包內目標相對目錄)]
my_datas = [
    ('config.json', '.'),
    ('assets/logo.png', 'assets'),
]
# 自動收集依賴套件的 metadata (解決 PackageNotFoundError)
my_datas += copy_metadata('tqdm')
my_datas += copy_metadata('requests')

a = Analysis(
    ['main.py'],
    pathex=[],
    binaries=[],
    datas=my_datas,
    # 手動補齊動態隱藏模組
    hiddenimports=['requests', 'charset_normalizer', 'engineio.async_drivers.threading'],
    hookspath=['./custom_hooks'], # 載入專案自訂 Hooks
    hooksconfig={},
    runtime_hooks=[],
    # 明確剔除大型未使用的函式庫，進行極致瘦身
    excludes=['matplotlib', 'scipy', 'tkinter', 'unittest'],
    win_no_prefer_redirects=False,
    win_private_assemblies=False,
    cipher=block_cipher,
    noarchive=False,
)

pyz = PYZ(a.pure, a.zipped_data, cipher=block_cipher)

exe = EXE(
    pyz,
    a.scripts,
    a.binaries,
    a.zipfiles,
    a.datas,
    [],
    name='StockMonitor',
    debug=False,
    bootloader_ignore_signals=False,
    strip=False,
    upx=True,                                  # 啟用 UPX 壓縮
    upx_exclude=['vcruntime140.dll', 'qwindows.dll'], # 排除容易壓縮壞掉的 DLL
    runtime_tmpdir=None,
    console=False,                             # False 代表無黑框 GUI 模式
    disable_windowed_traceback=False,
    argv_emulation=False,
    target_arch=None,
    codesign_identity=None,
    entitlements_file=None,
    icon='app.ico',
    uac_admin=False,                           # 是否強制以管理員身分運行
)

配置好 .spec 規格檔後，打包指令極致優雅：

pyinstaller StockMonitor.spec --clean

八、關鍵底層：動態依賴與 Hook 機制深度解析

在 Python 3.8+ 與現代開源生態中，打包最常遇到的玄學報錯就是：

importlib.metadata.PackageNotFoundError: No package metadata was found for pydantic

這是因為現代 Python 套件習慣在 __init__.py 中使用 importlib.metadata.version('package_name') 動態讀取自身安裝時的 dist-info 資訊。但 PyInstaller 預設只打包代碼與模組，不會收集包的元數據！

解決方案：Hook 工具包

PyInstaller 官方提供了強大的 PyInstaller.utils.hooks 輔助工具集，可以直接在 .spec 檔中調用：

from PyInstaller.utils.hooks import (
    collect_data_files,      # 收集套件所有的靜態數據（如 html, json, 模型權重）
    collect_submodules,      # 遞迴收集套件所有的子模組
    collect_dynamic_libs,    # 收集套件所有的 dll / so 動態函式庫
    copy_metadata,           # 複製套件的 dist-info 詮釋資料
    collect_all              # 集合以上所有功能的一鍵大絕招！
)

# 範例 1：一鍵完整封裝 Playwright 瀏覽器驅動與依賴
datas_pw, binaries_pw, hidden_pw = collect_all('playwright')

# 範例 2：解決常見套件 metadata 遺失
my_datas += copy_metadata('pydantic')
my_datas += copy_metadata('pydantic_core')
my_datas += copy_metadata('fastapi')

自定義 Hook 腳本 (Custom Hook)

如果你開發了自己的內部公司 SDK，或者某開源套件在 PyInstaller 尚未被官方適配，可以建立一個名為 hook-my_package.py 的檔案放置在 custom_hooks/ 目錄：

# custom_hooks/hook-my_package.py
from PyInstaller.utils.hooks import collect_data_files, collect_submodules

# 宣告該套件需要一併收集的資料與隱藏模組
datas = collect_data_files('my_package')
hiddenimports = collect_submodules('my_package')

並在打包時帶入 --additional-hooks-dir=custom_hooks 即可自動生效！

九、Windows 多行程（Multiprocessing）死循環陷阱與 Fork 炸彈防護

⚠️ 極度高危警告： 在 Windows 平台下打包包含 multiprocessing 或 concurrent.futures.ProcessPoolExecutor 的程式時，若漏掉關鍵防護，會引發著名的 Fork 炸彈，使電腦在幾秒鐘內耗盡所有 CPU 與記憶體瞬間當機死機！

底層機制深度剖析：
Linux 擁有原生 fork() 系統調用，複製父進程的記憶體頁面來產生子行程；而 Windows 沒有 fork，它採用 spawn 機制——透過重新啟動一個全新的 Python 直譯器進程來執行子任務。在未打包時，Windows 調用的是 python.exe main.py。

然而，當被 PyInstaller 打包為 myapp.exe 之後，Windows 啟動子行程時，執行的竟然是 myapp.exe 本身！若程式入口沒有攔截，子行程會從腳本第一行開始重新執行整個主流程，再次衍生子進程……幾秒鐘內就會遞迴生成成百上千個 exe 進程，徹底癱瘓系統！

標準跨平台多行程防護模板

# main_multiprocess.py
import sys
import multiprocessing
from concurrent.futures import ProcessPoolExecutor

def cpu_heavy_worker(task_id: int) -> int:
    """模擬耗費 CPU 的背景運算任務"""
    total = sum(i * i for i in range(1000000))
    return task_id + total

def main():
    print("主程式正式啟動...")
    with ProcessPoolExecutor(max_workers=4) as executor:
        results = list(executor.map(cpu_heavy_worker, range(10)))
    print(f"所有多行程運算完成，產物數量: {len(results)}")

if __name__ == "__main__":
    # 【關鍵神咒】：必須在 if __name__ == '__main__': 的第一行強制調用！
    # 它會檢查當前是否為 PyInstaller 衍生出來的子行程。
    # 若是子行程，會直接接管進入子任務迴圈，防止再次重跑主程式邏輯！
    multiprocessing.freeze_support()
    
    # 支援 Windows GUI 模式下的標準輸出重定向保護
    if sys.platform.startswith('win'):
        multiprocessing.set_start_method('spawn', force=True)

    main()

十、反編譯真相與智慧財產權防護（Decompilation & IP Security）

許多企業與獨立開發者使用 PyInstaller 打包商業軟體，以為產生了 .exe 就能高枕無憂、保護商業原始碼。這完全是危險的自我安慰！

殘酷真相：5 秒內還原你的 Python 原始碼

PyInstaller 打包的本質只是一個自解壓 ZIP 封裝包 + CPython 直譯器。任何略懂逆向工程的人只需執行以下兩步，就能輕易拿回你的原始碼：

  1. 使用開源工具 pyinstxtractor.py： 
    python pyinstxtractor.py myapp.exe
    只需 3 秒，就能將 myapp.exe 完整拆解出目錄，並提取出入口檔案的字節碼 main.pyc。
  2. 使用反編譯器 pycdc (Decompyle++) 或 uncompyle6： 
    pycdc main.pyc > main.py
    瞬間 100% 還原出原本的 Python 語法結構、變數名稱與函數邏輯！

商業級 Python 智慧財產權防護三部曲

🛡️ 方案 1：Cython 編譯為原生 C 二進位庫（最推薦）

將核心演算法、商業邏輯模組（如 core_logic.py）透過 Cython 轉譯為 C 語言代碼，並使用 MSVC / GCC 編譯為 Windows .pyd 或 Linux .so 機器碼共享庫。PyInstaller 直接打包 .pyd，反編譯工具面對真實的 x86_64 機器碼只能望洋興嘆！

🔐 方案 2：使用專業混淆加密工具 (PyArmor)

PyArmor 是專門針對 Python 字節碼的高強度混淆工具。它會在字節碼層級進行動態加密，並注入反除錯與虛擬機器檢查機制：

# 1. 使用 pyarmor 混淆腳本
pyarmor gen -O dist_obf main.py

# 2. 將混淆後的產物送交 PyInstaller 打包
pyinstaller --onefile dist_obf/main.py

☁️ 方案 3：雲端化架構分離 (SaaS API)

將涉及企業核心商業機密、AI 模型權重或專利運算的部分部署在雲端 API 伺服器；本地發布的 exe 僅作為 GUI 前端介面或客戶端代理（Thin Client），從物理層面隔絕核心代碼洩漏的風險。

十一、大型 GUI (PyQt6 / PySide6) 與現代 Web-Desktop (PyWebView) 打包指南

1. PyQt6 / PySide6 踩坑：缺少平台插件 qwindows.dll

打包 Qt 應用程式後，最常見的崩潰是彈出對話框：qt.qpa.plugin: Could not find the Qt platform plugin "windows"。

解法： 這是因為 Qt 依賴 plugins/platforms/qwindows.dll 等周邊插件。在打包指令中加入 --collect-all PyQt6 或在 spec 檔中明確收集：

pyinstaller --windowed --onefile --collect-all PyQt6 --name="MyQtApp" main.py

2. 現代潮流：Python 後端 + HTML5/Vue 現代前端 (PyWebView)

現在越來越多工程師摒棄傳統笨拙的 Tkinter，採用輕量級的 pywebview 打造現代化桌面應用（利用系統內建的 Edge WebView2 或 WebKit，體積僅 20MB 左右，遠勝 150MB+ 的 Electron）：

# 打包包含 web 靜態前端資源的 pywebview 應用
pyinstaller --windowed --onefile \
  --add-data="web_dist;web_dist" \
  --collect-all pywebview \
  --name="ModernDesktopApp" \
  main.py

十二、CI/CD 自動化實戰：GitHub Actions 多平台交叉發布工作流

⚠️ 牢記鐵律：PyInstaller 無法交叉編譯（Cross-Compilation）！
你絕對不能在 Windows 系統上產出 Linux ELF 可執行檔或 macOS .app，反之亦然。要在多平台發布，必須在對應的作業系統環境中各打包一次。

透過 GitHub Actions 的雲端虛擬機矩陣（Matrix Build），可以實現推動 Git Tag 時自動在 Windows、macOS 與 Linux 伺服器同時打包並發布 Release：

# .github/workflows/package.yml
name: Build Executables & Multi-Platform Release

on:
  push:
    tags:
      - 'v*'

jobs:
  build:
    runs-on: ${{ matrix.os }}
    strategy:
      matrix:
        include:
          - os: windows-latest
            artifact_name: StockMonitor-windows-amd64.exe
            asset_path: dist/StockMonitor.exe
          - os: ubuntu-latest
            artifact_name: StockMonitor-linux-amd64
            asset_path: dist/StockMonitor
          - os: macos-latest
            artifact_name: StockMonitor-macos-universal
            asset_path: dist/StockMonitor

    steps:
      - name: 檢出專案代碼
        uses: actions/checkout@v4

      - name: 設定 Python 3.11 環境
        uses: actions/setup-python@v5
        with:
          python-version: '3.11'
          cache: 'pip'

      - name: 安裝專案依賴與 PyInstaller
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements.txt
          pip install pyinstaller

      - name: 執行打包
        run: |
          pyinstaller StockMonitor.spec --clean

      - name: 重命名產物
        shell: bash
        run: |
          mv ${{ matrix.asset_path }} dist/${{ matrix.artifact_name }}

      - name: 上傳打包產物至 GitHub Release
        uses: softprops/action-gh-release@v2
        with:
          files: dist/${{ matrix.artifact_name }}
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}

十三、高頻踩坑與除錯避坑手冊（Troubleshooting）

💥 痛點 1：雙擊 exe 瞬間閃退無任何報錯

診斷： 如果啟用了 --windowed 或 -w，一旦程式拋出未捕捉的 Exception，由於沒有 CMD 主控台承接輸出，視窗會毫秒級閃退關閉。

解法： 暫時拔掉 -w 重新打包成帶有 Console 的模式，並在終端機中透過命令提示字元手動執行 .\dist\app.exe，即可完整抓取 Traceback 錯誤堆疊。

📉 痛點 2：產物體積肥大高達 200MB~500MB

診斷： 使用了系統全域環境或 Anaconda 環境打包，將無關的科學運算庫全數納入。

解法： 1. 建立全新虛擬環境 (python -m venv .venv)；2. 在 .spec 的 excludes 中主動封殺無用重型庫（如 matplotlib、scipy、IPython）；3. 下載 UPX 壓縮工具並加入 PATH。

🔍 痛點 3：ModuleNotFoundError: No module named 'xxx'

診斷： 專案使用動態反射（如 importlib.import_module()），靜態依賴掃描器無法自動探測。

解法： 在打包參數補上 --hidden-import="xxx" 或在 spec 檔的 hiddenimports 清單中明確宣告。

🛡️ 痛點 4：Windows Defender / 防毒軟體報毒攔截

診斷： 由於黑客經常利用 PyInstaller 包裹惡意木馬，其通用的預編譯 Bootloader 特徵碼被眾多防毒軟體標記為潛在誤報威脅 (False Positive)。

解法： 1. 在本機從原始碼重新編譯 PyInstaller Bootloader（消除公版二進位特徵）；2. 購買數位代碼簽章證書（Code Signing Certificate）；3. 提交誤報樣本至微軟安全審查中心。

⚠️ 痛點 5：UPX 壓縮後特定 DLL 崩潰 (0xc0000005)

診斷： UPX 壓縮演算法對某些包含自校驗、TLS 執行緒局部儲存或大型 C++ 運行庫的動態庫（如 vcruntime140.dll、Qt 插件）可能會損壞其 PE 結構。

解法： 在命令列或 spec 檔中使用 --upx-exclude=vcruntime140.dll 與 --upx-exclude=qwindows.dll 予以排除。

🔁 痛點 6：RecursionError: maximum recursion depth exceeded

診斷： 某些複雜庫（如 Google Cloud、Torch、Boto3）模組結構極深，超出 Python 預設的 1000 層遞迴上限。

解法： 在 .spec 規格檔的最上方加入 import sys; sys.setrecursionlimit(5000) 提高遞迴上限。

🔒 痛點 7：SSLCertVerificationError 憑證驗證失敗

診斷： 打包後 requests 或 urllib 找不到根憑證 cacert.pem。

解法： 透過 --add-data 將 certifi/cacert.pem 封裝進去，或在代碼中透過 certifi.where() 動態傳遞憑證路徑。

👑 痛點 8：Windows 系統需要提權管理員身分

診斷： 程式碼涉及修改系統登錄檔、寫入 C:\Program Files、監控實體硬體驅動。

解法： 在打包時加上 --uac-admin 旗標，Windows 會自動在執行檔內嵌管理員提權資訊，雙擊時自動彈出 UAC「是/否」許可授權。

十四、總結與生產級打包檢核清單（Production Checklist）

交付 Python 可執行檔是軟體走向生產應用的「最後一哩路」。在正式對外分發前，請逐一核對以下生產環境檢查清單：

  • ✅ 環境隔離： 是否已在全新的獨立虛擬環境（venv 或 uv）中執行打包，避免產物体積膨脹？
  • ✅ 路徑安全： 所有靜態唯讀資產是否皆透過 sys._MEIPASS 讀取？所有持久化使用者資料是否寫入真實 APPDATA 或 exe 資料夾，而非臨時暫存區？
  • ✅ 多行程防護： Windows 專案若調用 multiprocessing，是否已在入口處加上 multiprocessing.freeze_support() 防範進程炸彈？
  • ✅ 詮釋資料完備： 是否已針對現代套件調用 copy_metadata()，防止 PackageNotFoundError 崩潰？
  • ✅ 規格檔納管： 是否保存並將 .spec 檔案提交至 Git 版本控制，確保建置成果完全可重現？
  • ✅ 智慧財產權考量： 若涉及核心商用專利算法，是否已透過 Cython 編譯為 .pyd 或使用 PyArmor 加密混淆？
  • ✅ 多平台驗證： 是否已在純淨的目標測試作業系統（未安裝 Python 的新機器或虛擬機）中完整測試運作無誤？
